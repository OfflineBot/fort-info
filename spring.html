📄 Folien-PDF anzeigen / herunterladen 1-Spring-Grundlagen.pdf

🎯 TL;DR — was du wirklich wissen musst

  • Spring Boot = Spring + Convention-over-Configuration. JAR statt Anwendungsserver.
  • Vier Kernprinzipien: Convention over Configuration · Modularisierung · Schichtenorientierung · Dependency Injection.
  • Schichten: Controller (HTTP) → Service (Logik) → Repository (DB). Aufruf nur in dieser Richtung.
  • Stereotypes: @Controller / @RestController / @Service / @Repository / @Component. Alle = Bean.
  • DI: Konstruktor-Injection bevorzugt — final-Felder, test-freundlich, explizite Pflicht-Abhängigkeiten.
  • Bean ≠ new: niemals selbst instanziieren — Spring verwaltet den Lebenszyklus.

⚠ Typische Fehler / Klausur-Stolperfallen

Die Punkte, an denen die meisten in der Klausur Federn lassen.

⚠ Bean direkt mit new erzeugen
Außerhalb des Spring-Containers ist es keine Bean — DI funktioniert nicht, Repository ist null, Tests umgehen die Klasse. Immer per Konstruktor injizieren lassen.
⚠ @Autowired auf Feld statt Konstruktor
Felder können dann nicht final sein, Tests brauchen Reflection oder Spring-Kontext. Konstruktor-Injection ist seit Spring 3.5 die empfohlene Variante.
⚠ Forgotten @Service / @Controller
Ohne Stereotype-Annotation findet der Component-Scan die Klasse nicht — Spring kennt sie nicht, DI an anderen Stellen schlägt mit „No qualifying bean of type ..." fehl.
⚠ Falsche Schichten-Reihenfolge
Service ruft Controller — niemals. Aufrufrichtung ist immer Controller → Service → Repository. Sonst zirkuläre Abhängigkeit + Verlust der Testbarkeit.

1.1 Was ist Spring Boot

Spring ist ein offenes Framework zur Erstellung von plattformunabhängigen Web-Anwendungen mit Java. Spring Boot setzt auf Spring auf und ergänzt Standardeinstellungen, damit man self-contained, ausführbare JAR-Dateien ohne separaten Anwendungsserver bekommt.

Die vier Kernprinzipien

  • Convention-over-Configuration — Best-Practice-Annahmen statt umfangreicher Konfiguration.
  • Modularisierung — kleine, erweiterbare Kernfunktionen.
  • Schichtenorientierung — klare Strukturierung von Funktionalität.
  • Dependency Injection — Objekte bekommen ihre Abhängigkeiten von Spring zugewiesen.

1.2 Schichtenmodell

Spring strukturiert eine Web-Anwendung in drei Schichten:

SchichtVerantwortungSpring-Stereotype
Presentation LayerHTTP-Schnittstelle: nimmt Anfragen entgegen, gibt Antworten zurück@Controller / @RestController
Business LayerFachliche Logik, orchestriert Repositories, transformiert Daten@Service
Persistence LayerDatenzugriff (lesen, schreiben, suchen)@Repository

Aufrufrichtung: Controller → Service → Repository. Niemals umgekehrt — der Service kennt keinen Controller, das Repository kennt keinen Service.

1.3 Beans & Stereotypes

Eine Spring Bean ist eine Java-Klasse, deren Lebenszyklus (Instanziierung, Konfiguration, Wiring, Zerstörung) vom Spring-Framework verwaltet wird. Beans werden nicht mit new erzeugt, sondern vom IoC-Container.

AnnotationBedeutung
@Componentgenerische Bean — Lebenszyklus von Spring verwaltet
@Servicefachliche Geschäftslogik (semantisches Tag)
@RepositoryDatenzugriff; Spring übersetzt Persistenz-Exceptions automatisch
@ControllerHTTP-Endpunkt für klassische MVC-Antworten (Templates)
@RestController@Controller + @ResponseBody — JSON-API

Beispiel aus dem Kurs (Aufgabe 1)

package de.dhbw.ravensburg.wp.mymoviedatabase.service;

import org.springframework.stereotype.Service;

@Service
public class MovieServiceImpl implements MovieService {
    @Override
    public String getName() {
        return "MovieServiceImpl";
    }
}

1.4 Dependency Injection (DI)

In Spring werden die Komponenten, von denen eine Bean abhängt, vom Container injiziert — die Bean selbst sucht/erzeugt nichts. Das reduziert Kopplung und erleichtert Tests (Mocks injizieren statt echter Implementierung).

Konstruktor-Injektion (vom Kurs bevorzugt)

@Controller
public class MovieControllerImpl implements MovieController {

    private MovieService movieService;
    private ArtistService artistService;

    // Spring injiziert beide Services über den Konstruktor
    public MovieControllerImpl(MovieService movieService, ArtistService artistService) {
        this.movieService = movieService;
        this.artistService = artistService;
    }

    @Override public String getName()              { return "MovieControllerImpl"; }
    @Override public String getMovieServiceName()  { return movieService.getName(); }
    @Override public String getArtistServiceName() { return artistService.getName(); }
}

Alternative: @Autowired auf Feld oder Setter — bei modernem Spring aber unbeliebt, weil Felder dann nicht final sein können und Tests schwerer werden.

ManualTestBean — Konzept aus dem Kurs

Im Kurs wird der DI-Effekt mit einer ManualTestBean demonstriert, die per @EventListener(ApplicationReadyEvent.class) beim Start einmalig den Controller aufruft und die Namen der gewireten Beans loggt:

@Component
@Slf4j
public class ManualTestBean {
    // Vorsicht — diese Klasse ist nur für Übungszwecke,
    // sie sollte nie in einer produktiven Applikation sein.

    MovieController movieController;

    ManualTestBean(MovieController movieController) {
        this.movieController = movieController;
    }

    @EventListener(ApplicationReadyEvent.class)
    public void callController() {
        log.info("Controller: "      + movieController.getName());
        log.info("MovieService: "    + movieController.getMovieServiceName());
        log.info("ArtistService: "   + movieController.getArtistServiceName());
    }
}

⚙ Aufgabe 1 — Service & Controller mit DI

Aufgabenstellung
📦 Starter-ZIP ✅ Lösungs-ZIP

Im Starter-Projekt sind ein MovieService und ein MovieController als Klassen ohne Interface gegeben. Sie sollen so umgebaut werden, dass:

  1. Service und Controller jeweils ein Interface + eine Impl-Klasse haben.
  2. Die Impl-Klassen mit dem korrekten Stereotyp annotiert sind (@Service / @Controller).
  3. Ein zusätzlicher ArtistService (mit Impl) angelegt und im Controller per Konstruktor-Injektion gewired wird.
  4. Die ManualTestBean beim Start den Controller aufruft und alle drei Bean-Namen loggt.

Wichtig: keine new-Aufrufe; alles über DI.

Interface:

public interface ArtistService {
    String getName();
}

Impl:

@Service
public class ArtistServiceImpl implements ArtistService {
    @Override public String getName() { return "ArtistServiceImpl"; }
}

Controller (Konstruktor-DI mit beiden Services) — siehe Codebeispiel oben unter §1.4.

Erwartete Log-Ausgabe nach Start:

Controller: MovieControllerImpl
MovieService: MovieServiceImpl
ArtistService: ArtistServiceImpl

⚙ Weitere Aufgabe 1 — SoundtrackService analog zur Aufgabe 1

Aufgabenstellung

Erweitere die Aufgabe-1-Struktur um einen SoundtrackService. Anforderungen wie in Aufgabe 1: Interface + Impl mit korrektem Stereotyp, Konstruktor-Injection im Controller, Log-Ausgabe via ManualTestBean.

  1. Interface SoundtrackService mit Methoden String getName() und List<String> listAll().
  2. Impl SoundtrackServiceImpl mit @Service.
  3. Im MovieController-Interface neue Methoden getSoundtrackServiceName() und getSoundtrackList().
  4. Konstruktor-Injection: alle drei Services (Movie/Artist/Soundtrack) im Controller.
  5. ManualTestBean loggt beim Start alle vier Bean-Namen + die Soundtrack-Liste.
// SoundtrackService.java
package de.dhbw.ravensburg.wp.mymoviedatabase.service;

import java.util.List;

public interface SoundtrackService {
    String getName();
    List<String> listAll();
}
// SoundtrackServiceImpl.java
package de.dhbw.ravensburg.wp.mymoviedatabase.service;

import org.springframework.stereotype.Service;
import java.util.List;

@Service
public class SoundtrackServiceImpl implements SoundtrackService {
    @Override public String getName() { return "SoundtrackServiceImpl"; }
    @Override public List<String> listAll() {
        return List.of("Dreaming of the Crash", "Cornfield Chase", "Dust", "Day One");
    }
}
// MovieController.java (Interface)
package de.dhbw.ravensburg.wp.mymoviedatabase.controller;

import java.util.List;

public interface MovieController {
    String getName();
    String getMovieServiceName();
    String getArtistServiceName();
    String getSoundtrackServiceName();
    List<String> getSoundtrackList();
}
// MovieControllerImpl.java
package de.dhbw.ravensburg.wp.mymoviedatabase.controller;

import de.dhbw.ravensburg.wp.mymoviedatabase.service.ArtistService;
import de.dhbw.ravensburg.wp.mymoviedatabase.service.MovieService;
import de.dhbw.ravensburg.wp.mymoviedatabase.service.SoundtrackService;
import org.springframework.stereotype.Controller;
import java.util.List;

@Controller
public class MovieControllerImpl implements MovieController {

    private final MovieService      movieService;
    private final ArtistService     artistService;
    private final SoundtrackService soundtrackService;

    public MovieControllerImpl(MovieService movieService,
                               ArtistService artistService,
                               SoundtrackService soundtrackService) {
        this.movieService      = movieService;
        this.artistService     = artistService;
        this.soundtrackService = soundtrackService;
    }

    @Override public String getName()                  { return "MovieControllerImpl"; }
    @Override public String getMovieServiceName()      { return movieService.getName(); }
    @Override public String getArtistServiceName()     { return artistService.getName(); }
    @Override public String getSoundtrackServiceName() { return soundtrackService.getName(); }
    @Override public List<String> getSoundtrackList()  { return soundtrackService.listAll(); }
}
// ManualTestBean.java (Update)
@Component
@Slf4j
public class ManualTestBean {
    private final MovieController movieController;

    ManualTestBean(MovieController movieController) {
        this.movieController = movieController;
    }

    @EventListener(ApplicationReadyEvent.class)
    public void callController() {
        log.info("Controller:    " + movieController.getName());
        log.info("MovieService:  " + movieController.getMovieServiceName());
        log.info("ArtistService: " + movieController.getArtistServiceName());
        log.info("Soundtrack:    " + movieController.getSoundtrackServiceName());
        log.info("Tracks:        " + movieController.getSoundtrackList());
    }
}

⚙ Weitere Aufgabe 2 — Drei Injection-Typen vergleichen

Aufgabenstellung

Die Folien zeigen drei Wege der Dependency Injection: Constructor Injection, Setter Injection und Field Injection. Implementiere jede einmal und beschreibe die Trade-offs.

  1. Variante A: Constructor Injection (aktuell in Aufgabe 1).
  2. Variante B: Setter Injection mit @Autowired über dem Setter.
  3. Variante C: Field Injection mit @Autowired direkt am Feld.
  4. Diskutiere: Welche Variante erlaubt final-Felder? Welche ist test-freundlich? Welche kann zur Laufzeit eine Komponente wechseln?

A — Constructor Injection (Best-Practice laut Spring 3.5+):

@Controller
public class MovieControllerImpl implements MovieController {
    private final MovieService movieService;

    public MovieControllerImpl(MovieService movieService) {
        this.movieService = movieService;
    }
}

B — Setter Injection:

@Controller
public class MovieControllerImpl implements MovieController {
    private MovieService movieService;

    @Autowired
    public void setMovieService(MovieService movieService) {
        this.movieService = movieService;
    }
}

C — Field Injection:

@Controller
public class MovieControllerImpl implements MovieController {
    @Autowired
    private MovieService movieService;
}

🧠 Verständnis-Checks

Klick auf „Antwort anzeigen" — schnelles Selbstabfragen ohne Scrollen.

Welche Stereotype-Annotation für Business-Logik, DB-Zugriff, HTTP-API?

Antwort anzeigen
Business-Logik: @Service · DB-Zugriff: @Repository · HTTP-API klassisch: @Controller, REST: @RestController. Funktional sind alle drei @Component + semantischer Marker.

Was passiert, wenn ich new MovieServiceImpl() direkt im Controller aufrufe?

Antwort anzeigen
Du umgehst Spring komplett: das Objekt ist keine Bean, keine DI funktioniert, eingebettete Abhängigkeiten (Repository) sind null. Du verlierst Testbarkeit und Lifecycle-Management. Niemals tun.

Warum bevorzugt der Kurs Konstruktor-Injection gegenüber @Autowired auf Feldern?

Antwort anzeigen
Konstruktor-Injection erlaubt final-Felder (Immutability), macht Abhängigkeiten explizit (man sieht im Konstruktor was die Klasse braucht), und vor allem: in Tests kannst du Mocks direkt per Konstruktor übergeben — ohne Spring-Kontext, ohne Reflection.

Was bedeutet Convention over Configuration in Spring Boot?

Antwort anzeigen
Spring Boot trifft Best-Practice-Standardannahmen statt zu verlangen, dass du jedes Detail konfigurierst. Beispiel: Templates landen in src/main/resources/templates/, statische Dateien in static/ — automatisch, ohne XML.

Was macht @EventListener(ApplicationReadyEvent.class)?

Antwort anzeigen
Spring ruft die annotierte Methode genau einmal auf, sobald die Anwendung vollständig hochgefahren und alle Beans gewired sind. Im Kurs benutzt das die ManualTestBean, um beim Start einen Controller-Aufruf zu loggen.

Was ist der Unterschied zwischen @Component und @Service?

Antwort anzeigen
Funktional nichts — beide registrieren die Klasse als Bean. Semantisch: @Service markiert die Klasse als Business-Schicht (lesbarer für andere Entwickler, manche Tools wie Spring AOP nutzen das Tag).
