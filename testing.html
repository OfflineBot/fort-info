🎯 TL;DR — was du wirklich wissen musst

  • Test-Pyramide: viele Unit-Tests · einige Integrationstests · wenige Systemtests.
  • Best-Practice-Naming: Testklasse XTest, Testmethode shouldXBecauseY — Erfolg & Fehler je extra.
  • Test-Doubles: Fake (manuell, voll) · Stub (semi-auto, Antwortverhalten) · Mock (auto, Aufruf-Verhalten).
  • @WebMvcTest: startet nur den MVC-Layer. Services per @MockBean mocken.
  • MockMvc simuliert HTTP-Requests im Test (kein echter Server). perform(get(…)).andExpect(status().isOk()).
  • JsonPath: $=root · $[0]=erstes Array-Element · $.field · $[0].nested[1].x · $.*=alle Kinder.
  • Constraint-Violation: kein when() nötig — Service wird nie aufgerufen. verify(service, never()) beweist es.

⚠ Typische Fehler / Klausur-Stolperfallen

Die Punkte, an denen die meisten in der Klausur Federn lassen.

⚠ Mock-Bean ohne when() aufrufen
Mockito gibt dann den Default zurück: null, 0, oder leere Liste — egal welche Logik der echte Service hat. Pro Test alle nötigen Stubs aufsetzen.
⚠ JsonPath: $.title auf einer Array-Antwort
Bei Liste musst du den Index angeben: $[0].title. $.title auf einer Liste matcht nichts.
⚠ Long-IDs als JSON-Asserts ohne .intValue()
Jackson serialisiert kleine Long als int. jsonPath("$.id", is(1L)) schlägt fehl — du brauchst is(1) oder is(movie.getId().intValue()).
⚠ Constraint-Violation-Test mit when()
Bei @Valid-Verletzung passiert der Service-Call gar nicht. when(...) ist sinnlos. Statt dessen: verify(service, never()) nach dem Mock-Aufruf.
⚠ @WebMvcTest mit @Autowired-Service
Services werden nicht geladen. @MockBean ist Pflicht für jede Service-Abhängigkeit, sonst wirft der Test „No qualifying bean".
⚠ Test-Klassen-Naming verletzt
Folien-Konvention: X-Test heißt XTest (ohne Underscore, Test als Suffix). Test-Methoden mit should + Verhalten beginnen — sonst Punktabzug bei Code-Review.

4.1 Test-Pyramide

Im Kurs wird die klassische Pyramide unterrichtet:

  1. Unit-Tests — testen eine einzelne Klasse / Methode isoliert. Schnell, viele.
  2. Integrationstests — testen das Zusammenspiel mehrerer Komponenten (z.B. Controller + Service + Repository). Mittlere Anzahl.
  3. Systemtests — testen die ganze Anwendung end-to-end (HTTP rein, JSON raus, evtl. DB). Wenige, langsam.

Faustregel: wenig Systemtests, viele Unit-Tests, mittel viele Integrationstests.

4.2 JUnit 5 Basics

import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

class MovieServiceTest {

    private MovieService service;

    @BeforeEach
    void setUp() { service = new MovieServiceImpl(...); }

    @Test
    @DisplayName("findAll liefert alle Filme")
    void findAll() {
        var movies = service.getAllMovies();
        assertEquals(2, movies.size());
    }

    @Test
    void findByIdWirftWennNichtVorhanden() {
        assertThrows(NoSuchElementException.class,
            () -> service.getMovieById(999L));
    }
}

Lifecycle: @BeforeAll (static), @BeforeEach, @AfterEach, @AfterAll (static). Außerdem nützlich: @DisplayName, @Disabled, @Tag.

4.3 Test Doubles & Mockito

Test Double = Sammelbegriff für Ersatzobjekte. Im Spring-Kontext:

  • Dummy — wird übergeben, aber nie genutzt.
  • Stub — gibt vordefinierte Antworten zurück.
  • Mock — wie Stub, plus Verifikation der Aufrufe.
  • Spy — echtes Objekt, einzelne Methoden überschrieben.
  • Fake — eigene, vereinfachte Implementierung (z.B. In-Memory-Repo).
import static org.mockito.Mockito.*;

@Test
void mockBeispiel() {
    MovieService mock = mock(MovieService.class);
    when(mock.getMovieById(1L)).thenReturn(new MovieDTO(...));

    var result = mock.getMovieById(1L);
    assertNotNull(result);

    verify(mock).getMovieById(1L);
    verify(mock, never()).getAllMovies();
}

4.4 MockMvc & @WebMvcTest

@WebMvcTest(controllers = X.class) startet nur den MVC-Layer (kein voller Kontext, keine DB) und gibt dir MockMvc zum Aufruf der Endpoints. Service-Beans werden mit @MockBean gemockt.

@WebMvcTest(controllers = MovieControllerImpl.class)
public class MovieControllerImplTest {

    @MockBean    private MovieService movieService;
    @Autowired   private MockMvc      mockMvc;
    @Autowired   private ObjectMapper objectMapper;

    private MovieDTO movie_1;

    @BeforeEach
    public void setUp() {
        movie_1 = new MovieDTO(1L, "Interstellar", 2.49, /* ... */ );
    }

    @Test
    public void shouldReturnMovieById() throws Exception {
        when(movieService.getMovieById(1L)).thenReturn(movie_1);

        mockMvc.perform(get("/api/v1/movies/1"))
               .andExpect(status().isOk())
               .andExpect(jsonPath("$.title", is("Interstellar")));

        verify(movieService).getMovieById(1L);
    }

    @Test
    public void shouldReturn404WhenIdUnknown() throws Exception {
        when(movieService.getMovieById(anyLong()))
            .thenThrow(new NoSuchElementException("not found"));

        mockMvc.perform(get("/api/v1/movies/20"))
               .andExpect(status().isNotFound());
    }
}

4.5 JsonPath

Mit jsonPath("$.feld", matcher) prüfst du gezielt einzelne Felder im JSON-Response.

JsonPathBedeutung
$Wurzel
$.titleFeld title
$[0]erstes Array-Element
$.*alle direkten Kinder
$.awards[0].academyverschachtelt

Beliebte Hamcrest-Matcher (statisch importiert über org.hamcrest.Matchers.*):

.andExpect(jsonPath("$.*", hasSize(2)))
.andExpect(jsonPath("$[0].title", is("Interstellar")))
.andExpect(jsonPath("$.castIds", containsInAnyOrder(1, 2, 4)));

⚙ Weitere Aufgabe 2 — @BeforeEach + Helper-Methoden

Aufgabenstellung

Die Folien empfehlen explizit, wiederholten Test-Setup-Code in @BeforeEach / @BeforeAll + Helper-Methoden auszulagern. Refactor des MovieControllerImplTest:

  1. Erstelle die Test-Movies in einer privaten Helper-Methode makeMovie(id, title, rating).
  2. Verschiebe das Setup in @BeforeEach setUp() — frische Objekte vor jedem Test.
  3. Wenn ein Setup teuer wäre (z.B. Datei laden): @BeforeAll static nutzen, einmalig.
  4. Erkläre, warum @BeforeAll als static deklariert werden muss.
@WebMvcTest(controllers = MovieControllerImpl.class)
class MovieControllerImplTest {

    @MockBean    private MovieService movieService;
    @Autowired   private MockMvc      mockMvc;
    @Autowired   private ObjectMapper objectMapper;

    private MovieDTO movie_1;
    private MovieDTO movie_2;
    private List<MovieDTO> movieList;

    @BeforeEach
    void setUp() {
        movie_1 = makeMovie(1L, "Interstellar",   8.6);
        movie_2 = makeMovie(2L, "The Dark Knight", 9.0);
        movieList = List.of(movie_1, movie_2);
    }

    private MovieDTO makeMovie(Long id, String title, double rating) {
        MovieDTO m = new MovieDTO();
        m.setId(id);
        m.setTitle(title);
        m.setImdbRating(rating);
        m.setTrailerUrl("https://example/" + id);
        return m;
    }

    @Test
    void shouldReturnAllMovies() throws Exception {
        when(movieService.getAllMovies()).thenReturn(movieList);
        mockMvc.perform(get("/api/v1/movies"))
               .andExpect(status().isOk())
               .andExpect(jsonPath("$.*", hasSize(2)));
    }
}

Warum static bei @BeforeAll? Weil die Methode vor der Instanziierung der Testklasse läuft — es gibt also noch kein this. Spring/JUnit ruft sie als Klassenmethode auf.

Lehre aus den Folien: "Beim Verfassen der Testmethoden ist darauf zu achten, dass sich wiederholender Code bezüglich des Aufbaus der zu testenden Objekte in Hilfsmethoden ausgelagert wird."

⚙ Weitere Aufgabe 3 — Stub vs. Mock am MovieService

Aufgabenstellung

Die Folien stellen den Unterschied zwischen Stub und Mock am Banking-Beispiel dar: Stub bildet Antwortverhalten nach (Stand 100€ → 80€), Mock prüft nur den Aufruf. Übertrage diese Unterscheidung auf den MovieService:

  1. Stub-Stil: simuliere movieService.getMovieById(1L) → movie_1 und prüfe den Rückgabewert (Fokus: Zustand/Ergebnis).
  2. Mock-Stil: simuliere removeMovieById(1L) ohne Rückgabe und verifiziere nur, dass die Methode aufgerufen wurde (Fokus: Aufruf-Verhalten).
  3. Schreibe beides als Test-Methoden im selben MovieControllerImplTest.
  4. Erkläre, warum der Stub-Stil jsonPath-Assertions hat, der Mock-Stil aber nur verify().

Stub-Stil — Fokus: Ergebnis

@Test
void stubStyle_returnsCorrectMovie() throws Exception {
    // Stub: vorbereitetes Antwortverhalten
    when(movieService.getMovieById(1L)).thenReturn(movie_1);

    // Evaluiert den ZUSTAND der Response (=Stub-Fokus laut Folie)
    mockMvc.perform(get("/api/v1/movies/1"))
           .andExpect(status().isOk())
           .andExpect(jsonPath("$.title",   is("Interstellar")))
           .andExpect(jsonPath("$.imdbRating", is(8.6)));
}

Mock-Stil — Fokus: Aufruf

@Test
void mockStyle_deleteCallsService() throws Exception {
    // Kein when() — wir interessieren uns nicht für eine Rückgabe.
    doNothing().when(movieService).removeMovieById(1L);

    mockMvc.perform(delete("/api/v1/movies/1"))
           .andExpect(status().isOk());

    // Evaluiert das AUFRUF-VERHALTEN (=Mock-Fokus laut Folie)
    verify(movieService, times(1)).removeMovieById(1L);
    verify(movieService, never()).addMovie(any());
}

Warum die unterschiedlichen Assertions? Beim Stub ist die Antwort interessant — also prüfen wir per jsonPath das JSON. Beim Mock ist die Antwort egal (z.B. void-Methode) — wir prüfen nur, dass die Komponente überhaupt korrekt aufgerufen wurde.

⚙ Weitere Aufgabe 4 — JsonPath im Detail

Aufgabenstellung

Die offizielle Aufgabe-6-Lösung nutzt rund 30 verschiedene jsonPath-Ausdrücke — wenn du sie nicht beherrschst, schreibst du im Kurztest blind. Übe alle Patterns am MovieDTO:

Gegeben sei diese JSON-Antwort des MovieControllers:

[
  {
    "id": 1,
    "title": "Interstellar",
    "duration": 2.49,
    "imdbRating": 8.6,
    "castIds": [4, 7, 11],
    "awards": [
      { "id": 1, "academy": "Oscar", "category": "Best VFX", "celebrationYear": 2015 }
    ]
  },
  {
    "id": 2,
    "title": "The Dark Knight",
    "duration": 2.32,
    "imdbRating": 9.0,
    "castIds": [1, 2],
    "awards": [
      { "id": 2, "academy": "Oscar", "category": "Supporting Role", "celebrationYear": 2009 },
      { "id": 3, "academy": "Oscar", "category": "Sound Editing",   "celebrationYear": 2009 }
    ]
  }
]

Schreibe die passenden jsonPath-Assertions für:

  1. „Die Antwort enthält genau 2 Filme."
  2. „Der erste Film heißt Interstellar."
  3. „Der zweite Film hat IMDB-Rating 9.0."
  4. „Der zweite Film hat 3 Cast-Ids und enthält die ID 1 und 2 (Reihenfolge egal)."
  5. „Der erste Award des ersten Films ist von der Oscar Academy."
  6. „Der zweite Award des zweiten Films hat das Jahr 2009."
  7. Bei einer Antwort die nur ein Movie ist (nicht Array): „Der Movie heißt Interstellar."
  8. Bei einer Antwort die nur ein Movie ist: „Der erste Award hat ID 1."
// 1. Anzahl Filme
.andExpect(jsonPath("$.*", hasSize(2)))

// 2. Titel des ersten Films
.andExpect(jsonPath("$[0].title", is("Interstellar")))

// 3. Rating des zweiten Films
.andExpect(jsonPath("$[1].imdbRating", is(9.0)))

// 4. CastIds des zweiten Films
.andExpect(jsonPath("$[1].castIds", hasSize(2)))
.andExpect(jsonPath("$[1].castIds", containsInAnyOrder(1, 2)))

// 5. Erster Award des ersten Films
.andExpect(jsonPath("$[0].awards[0].academy", is("Oscar")))

// 6. Zweiter Award des zweiten Films
.andExpect(jsonPath("$[1].awards[1].celebrationYear", is(2009)))

// 7. Bei Einzel-Objekt: kein Index, direkt $.field
.andExpect(jsonPath("$.title", is("Interstellar")))

// 8. Bei Einzel-Objekt mit verschachteltem Array
.andExpect(jsonPath("$.awards[0].id", is(1)))

Pattern-Übersicht:

PatternBedeutung
$Wurzel
$.fieldFeld in einem Objekt
$[0]Erstes Element eines Arrays
$[0].fieldFeld des ersten Elements
$.*Alle direkten Kinder — kombiniert mit hasSize zur Längen-Prüfung
$[0].awards[0].categoryVerschachtelt: Award-Kategorie des ersten Awards des ersten Films

Wichtige Hamcrest-Matcher dazu:

  • is(value) — exakter Vergleich (das gängigste)
  • hasSize(n) — Anzahl Elemente in Array/Objekt
  • containsInAnyOrder(a, b, c) — Array enthält genau diese Werte, Reihenfolge egal

Typische Fehler in Klausuren:

  1. Long vs int: JSON-IDs werden als int deserialisiert. is(movie_1.getId()) schlägt fehl — schreib is(movie_1.getId().intValue()).
  2. Index vergessen bei Arrays: $.title auf einer Array-Antwort gibt nichts zurück. Du brauchst $[0].title.
  3. $.* missverstanden: bei einer Liste mit 2 Objekten ist $.*-hasSize = 2 (Anzahl Objekte). Bei einem Einzel-Objekt mit 5 Feldern ist $.*-hasSize = 5 (Anzahl Felder).

⚙ Weitere Aufgabe 5 — Constraint-Violation-Tests (Validation-Chain)

Aufgabenstellung

Die offizielle Lösung testet Validierungs-Fehler an mehreren Stellen. Verstehe das Pattern: bei einer @Valid-Violation läuft der Request nicht bis zum Service durch — Spring antwortet direkt mit 400.

Folgender MovieDTO hat zwei pflichtige Felder:

@Getter @Setter @NoArgsConstructor
public class MovieDTO {

Pattern, das du dir merken musst:

  1. Kein when() in Constraint-Violation-Tests — der Service wird ja nie aufgerufen, also gibt es nichts zu stubben.
  2. Pflicht: verify(service, never()) — beweise dass der Validator den Request abgefangen hat.
  3. Erwarteter Status: 400, nicht 422 oder 500.

Folien-Beleg: in der Lösung zu Aufgabe 6 finden sich genau diese Methoden: shouldFailUpdateMovieBecauseConstraintViolation, shouldFailAddNewMovieDueToConstraintViolation, jeweils mit dem Kommentar „kein when weil Contraint Violation VOR dem Controller geworfen wird".

Wie sollen Testmethoden laut Folie heißen?

Mit Präfix should + dem zu testenden Verhalten — sowohl Erfolgs- als auch Fehlerfall: shouldSuccessfullyLogin, shouldNotLoginBecauseWrongPassword, shouldNotLoginBecauseEmptyPassword.

Wo liegt der Test-Ordner und wie soll seine Struktur aussehen?

Antwort anzeigen
src/test/. Die Package-Struktur muss identisch zu src/main/ sein — sonst funktioniert die DI von Spring beim Laden der Test-Beans nicht zuverlässig.

Erkläre die drei Test-Arten der Pyramide kurz.

Antwort anzeigen
Unit-Test: einzelne Methode/Klasse isoliert. Integrationstest: Zusammenspiel mehrerer Komponenten (z.B. Controller→Service→Repo). Systemtest: gesamte Anwendung inkl. nicht-funktionaler Anforderungen, möglichst nahe am Produktivsystem.

Was ist die zentrale Herausforderung bei Unit-Tests in Spring, die Test-Doubles lösen?

Antwort anzeigen
Klassen haben Abhängigkeiten zu anderen (Controller→Service→Repo). Um eine Methode isoliert zu testen, ersetzt man die Abhängigkeit durch ein Test-Double — die echte Implementierung wird nicht aufgerufen.

Erkläre Fake vs. Mock vs. Stub gemäß Kurs.

Antwort anzeigen
Fake: eigenständig geschriebene Alternativ-Implementierung mit reduzierter Komplexität (aufwändig). Mock: automatisch generiert, Standard-Rückgaben, Fokus auf Aufruf-Verhalten. Stub: semi-automatisch, angepasstes Antwortverhalten, Fokus auf Zustand/Ergebnis.

Banking-Beispiel: was prüft ein Stub vs. ein Mock bei einer Überweisung?

Antwort anzeigen
Stub bildet das Konto-Antwortverhalten nach (Stand 100€ → Transaktion → Stand 80€) und prüft den Endzustand. Mock prüft nur, ob der Transaktionsbefehl korrekt an den Bankserver geschickt wurde — nicht den Kontostand.

Welche Annotation verwandelt eine Klasse im Spring-Test in einen Mock?

Antwort anzeigen
@MockBean auf dem Feld. Spring ersetzt damit die echte Bean im Test-Kontext durch eine Mockito-Mock-Implementierung — alle Methoden geben Defaults zurück, bis du sie mit when().thenReturn() stubbst.

Was startet @WebMvcTest(controllers = X.class)?

Antwort anzeigen
Nur den MVC-Layer (Controller + ControllerAdvice + Filters) für die genannte Klasse. Kein Service-, Repository- oder DB-Bean wird geladen — alle Service-Abhängigkeiten musst du per @MockBean mocken. Ergebnis: schnelle Tests.

Was ersetzt MockMvc gegenüber Postman?

Antwort anzeigen
Postman ist manuelles HTTP-Aufrufen. MockMvc simuliert HTTP-Requests im Test ohne echten Server zu starten — du kannst URL, Methode, Header, Body steuern und Status, Headers, JSON-Body assertieren.

Schreibe ein Stub für: movieService.getMovieById(1L) soll movie_1 zurückgeben.

Was prüft verify(movieService, never()).addMovie(any()) und wann ist das relevant?

Antwort anzeigen
Es prüft, dass addMovie nicht aufgerufen wurde. Relevant z.B. bei Constraint-Violation-Tests: wenn der Validator vor dem Controller schlägt, darf der Service gar nicht erst angefasst werden.

Warum hat dieser Test kein when()?

movie_1.setTrailerUrl(null);
mockMvc.perform(post("/api/v1/movies")
  .contentType(APPLICATION_JSON)
  .content(objectMapper.writeValueAsString(movie_1)))
  .andExpect(status().isBadRequest());

Antwort anzeigen
Weil die @Valid-Constraint-Violation vor dem Controller geworfen wird — der Service wird nicht aufgerufen, also gibt es nichts zu stubben. Stattdessen prüft man am Ende per verify(service, never())….

Welche zwei JUnit-Lifecycle-Annotationen werden im Kurs für Setup empfohlen, und wofür?

Antwort anzeigen
@BeforeAll (statisch, einmal pro Testklasse) für teures Setup; @BeforeEach (vor jeder Testmethode) für frische Test-Objekte, damit kein Test den anderen beeinflusst.
